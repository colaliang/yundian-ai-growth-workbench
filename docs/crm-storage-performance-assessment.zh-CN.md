# CRM JSON 存储性能评估（D1 / D2 本地证据）

2026-10-16。范围是私有部署的存储演进评估；未更换数据库、迁移客户数据或改变备份格式。

## 实测结论

D1 Linux 原生 /tmp、相同硬件/Node22.18、同规模确定性假数据：500 条五流程各 1 次预热、3 次采样，复用读取、投影索引及停用备份内部检查共同使中位数改善 3.02–6.08 倍。查询 12219.33→3862.33ms，详情 23436.08→3971.47ms，漏斗 12689.19→3921.52ms，导出 23465.31→3859.89ms，首页 12203.76→4042.31ms。3 样本的 p95 只是最大值，不能作为容量承诺。原始证据见 .superpowers/sdd/2026-10-13-d-crm-performance-plan/benchmark-report.md 及 linux-results/。

D1 的十次 5000 条 HTTP 流程均在 120 秒全流程边界被截止，不能计算延迟分布或改善倍数。独立单次 GET state 功能证明最终 HTTP200、5000 条、7493819 字节，全子进程约381秒；它只证明该次完整读取可完成，不代表交互可用。

D2 Windows 同一 21 条假数据，一次完整 GET200 55973 字节/2399.724ms，摘要 GET200 47184 字节/2432.718ms，分页 POST200 16059 字节/2354.190ms、20 行/总21。摘要与分页共两次请求，共63243字节，大于该小数据完整读取；不声称总体流量或速度下降。D2 纯查询测试覆盖5000条的页数、范围、筛选和选择正确性，与实际HTTP容量不同。

D2 原 Linux5000尝试被宿主中断，只有认证/造数日志，无查询完成证据。唯一一次新输出重试：空数据认证63.696ms，250公司/500联系人/5000线索/10000跟进造数816.155ms；正常读快照下规范版本前置计算222421.755ms，随后真实发出一次分页POST。全子进程600114.293ms被外部600000ms截止，SIGTERM，无HTTP响应/最终JSON。5000分页HTTP200/20行/总5000验收仍未满足；交互延迟不可接受。没有重复采样或冷启动SLA。

## 成本来源与选择

当前分页限制网络结果行数，但正常鉴权、工作区修订、规范摘要和全量引用校验仍必须读取当前JSON集合。源代码的跨记录逐条查找/引用校验存在随数据规模近似二次增长的成本；不能将分页响应变小解释为端到端存储复杂度已解决。D1请求内索引只消除部分重复工作，未绕开规范版本和B3协调器。

|候选|可保留的能力|需要解决的问题|应先验证的边界|
|---|---|---|---|
|JSON加持久索引|现有逐文件格式、可检查导出、现有恢复兼容|索引不能成为第二真相；索引失效、重建与规范修订必须协调；每次仍全盘扫描则收益有限|同修订结果相等、外部文件变化检测、索引丢失重建、崩溃恢复、隔离与篡改拒绝|
|SQLite原型|可评估索引查询/关联及事务整合，尚未实现或测量|业务原子写、租户/实例身份、备份恢复和旧Snapshot兼容均需重新设计；不能只把分页表换库就宣称完成|导入导出逐字段等价、同范围CSV、历史漏斗、写冲突/401/409、事务故障恢复、备份恢复及回滚|

建议另立可逆原型验证：先在独立假数据上比较完整端到端请求、规范版本、内存、读取量和恢复行为，再决定是否采用持久索引或SQLite。当前证据不能给出SQLite加速数值，也不能批准客户迁移。

## 迁移与客户安全验收

任何后续原型均应保留现有客户/实例UUID、B3独占写入与修订守卫、明确未分配与停用历史身份、来源记录和附件引用；禁用混合后端双写。迁移前完整备份，离线转换到新目标，逐集合记录计数、ID、字段、引用与规范范围校验；新目标验收前保持旧目录可回退。备份必须包含足够的数据库/索引版本与一致性元数据；旧导出与恢复链路先证明兼容，再考虑切换。

验收必须补齐500/5000所有规定流程真实HTTP200及正确行数，标明预热、样本数、平台、端点和前置成本；检查故障中断、陈旧修订零副作用、跨客户拒绝、恢复后同结果。实际客户数据迁移、云端、付费服务、生产发布和五用户试用均不在本轮证据范围。
